## 1. 前提と目的

### 1.1 現状の課題
DiscordのAIオフィスは「おしゃべりするだけ」で止まっている。
- 部門AIが「どらが何してるか」を把握していない
- Discordからの指示が実行されない（チャット返答のみ）
- 会議・日報の前提知識が薄く、中身のない議論になる
- Discordでの会話・指示が記録に残らず揮発する

### 1.2 あるべき姿
**DiscordはClaude Codeのリモコンであり、AIオフィスの住みか。**
- 全部門AIが自分の担当Claude Codeセッションの中身を完全把握
- Discordからの指示で実際にClaude Codeが動き、成果物を出す
- 会話・指示・実行結果が全てログとして残る
- どら不在でも自律的に動き、戻ったら報告される

### 1.3 登場人物と関係

```
どら（CEO）
  ├── Claude Code（直接セッション）── 各部門の作業場
  ├── Discord（AIオフィス）── 外からの指示・会話・報告の場
  └── shared_state.json ── 全部門の状態を一元管理する「背骨」
```

## 3. 追加で検討すべきパターン

### P-17: 成果物のDiscordアップロード
- 生成したPDF/HTML/画像をDiscordの📦チャンネルに直接アップロード
- ファイルサイズ制限（Discord: 25MB）への対処

### P-18: 通知の粒度制御
- 全部の活動を通知すると**ノイズで埋もれる**
- どら向け通知 vs 部門間通知 vs ログ用記録の3段階
- Discord側で「重要度」フィルターをかける仕組み

### P-19: ロールバック・取り消し
- Discordから「さっきの指示取り消し」
- git revert or ファイル復元の仕組み
- 実行前の確認ステップ（危険度に応じて）

### P-20: 外部イベント → Discord → 対応
- GitHub PR/Issue → Discord通知 → 部門AIが対応
- VPSアラート → Discord通知 → セキュリティ部が対応
- スケジュール（cron）→ 定期タスク実行 → 結果報告

## 4. リスク分析

### 4.1 データ整合性リスク

| リスク | 影響度 | 発生確率 | 対策 |
|--------|--------|---------|------|
| **shared_state同時書き込み破損** | 高 | 中 | fcntlロック + tmpファイル→atomic rename（実装済み）。DiscordBot側も同じパターンを厳守 |
| **Discord指示 vs Claude Codeセッション衝突** | 高 | 高 | dept_lock連携必須。ロック中部門への指示はキューに入れて待つ or 「今○○セッションが作業中です」と警告 |
| **stale data問題** | 中 | 高 | shared_stateのupdated_atを常にチェック。3日以上前のデータは「古い可能性あり」と明示 |
| **セッション要約の精度** | 中 | 中 | /compact や /handover 時に自動生成される要約を利用。手動メモに依存しない |

### 4.2 実行リスク

| リスク | 影響度 | 発生確率 | 対策 |
|--------|--------|---------|------|
| **Discord指示で誤ったコード変更** | 高 | 中 | 破壊的操作は必ずどらの確認を挟む。git commitで戻せる状態を維持 |
| **API呼び出しの暴走** | 高 | 低 | monthly_cost_cap（$30）で自動停止。rate_limit_per_minute（10回）制限 |
| **自律活動の品質** | 中 | 高 | 成果物生成時は品質ゲート通過必須。自発リサーチ結果は「未検証」タグ付き |
| **無限ループ** | 高 | 低 | 部門Aが部門Bに依頼→部門Bが部門Aに依頼→ループ。依頼チェーンの深さ制限（最大3段） |

### 4.3 ユーザー体験リスク

| リスク | 影響度 | 発生確率 | 対策 |
|--------|--------|---------|------|
| **通知爆弾** | 中 | 高 | 通知3段階分離（P-18）。どら向けはサマリーのみ |
| **応答遅延** | 中 | 中 | 重い処理はバックグラウンド実行→完了通知。即座に「承りました」返答 |
| **会話コンテキスト肥大化** | 中 | 高 | Discord会話ログは直近20件まで。古いものはファイルに退避 |
| **指示の解釈ミス** | 高 | 中 | 曖昧な指示には確認を返す。「○○ということでいいですか？」 |

## 6. 実装フェーズ

### Phase 1: 情報基盤（P-01〜P-04, P-11〜P-13）
**目標: 「知ってる状態」を作る**

- shared_stateにsession_summary追加
- Discord会話の自動記録（discord_log）
- 全部門AIに全体状況+セッション要約を注入（一部今日完了）
- セッション完了時のDiscord自動報告
- Discord会話→memory/への自動保存
- 日報の最終更新日表示（今日完了）

### Phase 2: 実行能力（P-05〜P-08）
**目標: 「やれる状態」を作る**

- 指示実行エンジン構築
- 安全な実行範囲の定義（許可コマンドホワイトリスト）
- 実行結果のDiscord報告
- 部門間依頼フローの自動化
- 成果物のDiscordアップロード（P-17）

### Phase 3: 自律・最適化（P-09, P-10, P-14〜P-20）
**目標: 「勝手に動く状態」を作る**

- 自発リサーチの実行能力

- エラー即座報告
- 競合防止（dept_lock連携）
- 通知粒度制御

## 8. 安全設計

### 8.1 実行権限マトリックス

| 操作 | Discord自動実行 | どら確認必要 | 禁止 |
|------|---------------|------------|------|
| ファイル読み取り | ○ | | |
| Web検索・リサーチ | ○ | | |
| レポート生成（MD） | ○ | | |
| スクリプト実行（既知） | ○ | | |
| ファイル編集 | | ○ | |
| git commit/push | | ○ | |
| LP/HTML生成 | | ○ | |
| 外部API呼び出し | | ○ | |
| 環境変数変更 | | | ✕ |
| .env編集 | | | ✕ |
| rm -rf / 破壊的操作 | | | ✕ |
| 外部送信（メール等） | | | ✕ |

### 8.2 コスト制御

| 制御 | 現状 | 追加 |
|------|------|------|
| 月額上限 | $30/月で自動停止 | 維持 |
| レート制限 | 10回/分 | 維持 |
| 実行コスト | なし | 1指示あたりの想定コスト表示。高コスト指示は確認 |
| ログサイズ | discord_activity_logに蓄積 | 30日で古いログ自動削除 |
| shared_stateサイズ | 54KB（健全） | 100KB超で自動圧縮（古いログ削除） |

### 8.3 バグ予防チェックリスト

| チェック項目 | 対策 |
|------------|------|
| shared_state.jsonのJSON破損 | tmpファイル書き込み→atomic rename（実装済み）|
| fcntlロックのデッドロック | タイムアウト付きロック（5秒）。取れなければリトライ3回→スキップ |
| Discord API レート制限 | 1秒間隔でメッセージ送信。バースト防止 |
| 指示実行の無限ループ | 依頼チェーン最大3段。同一指示の重複実行防止（指示ID管理） |
| メモリリーク | discord_logは直近100件に制限。古いものはファイルに退避 |
| Bot再起動時のデータ消失 | 全データはshared_state.json（ファイル）に永続化。メモリのみのデータなし |
| AI幻覚（存在しない部門） | 15部門ホワイトリスト（実装済み）|
| 「えむ」呼び問題 | プロンプトで厳禁（実装済み）|
| 時刻ズレ | 全てJST統一。datetime.now(JST)を一貫使用 |
| 文字コード | UTF-8統一。ensure_ascii=False |
